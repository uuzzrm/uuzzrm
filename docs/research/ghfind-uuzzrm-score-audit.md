# ghfind 对 uuzzrm 的评分审计

审计日期：2026-08-16。范围仅限公开 GitHub 信号与 ghfind 的开源实现；不代表对个人能力、私有工作或雇佣价值的结论。

## 已确认的本地基线

本次本地审计记录的 uuzzrm 基线为：**最终 64.3 / 100**，**基础分 74.3**，仅有一项红旗：`new_account_mass_repos`（-10）。其触发条件不是“项目不好”，而是“账号年龄小于一年且公开仓库数大于 30”。因此当前距离 70 分档只差 5.7 分；若其他采集数据不变，账号年龄跨过一年后该规则自然不再触发，理论上会回到基础分，但必须以届时的新扫描为准。

本地已确认的核心指标：**72 个已合并 PR**、**165 个 impact PR（高影响仓库 PR）**。主页 README 也保存了可人工核验的、按上游项目归组的合并 PR 目录；这对访客可读性有价值。扫描器会间接读取项目 README 来判断原创项目的完整度，但主页文案不能伪造 PR、账号年龄、生态影响或活动数据。

> 基线是本次研究任务提供并在本地工作记录中确认的快照，不冒充 ghfind API 的实时结果。2026-08-16 直接请求公开 API 被 Vercel 浏览器校验页拦截，因此没有用不可验证的网络响应覆盖此快照。

## 机器评分与 LLM 文案不是一回事

确定性引擎将六项子分相加为基础分，再减红旗处罚（处罚总额上限 40），并把结果限制在 0–100；同一组输入应得到同一分数。源码明确说明 LLM 不参与这个数字。网站的 LLM 流程只按已有分数、维度和证据写标签、锐评与报告；提示词还强制 `@@ADJUST 0@@`，禁止改分或自行加减分。

因此：完善 bio、README、名片式主页和“已合并贡献”目录，能够让人类访客与 LLM 报告更准确地理解工作；但不能靠漂亮文案直接把 64.3 改成高分。反过来，实质项目、被维护者合并的 PR、持续活动等公开事实，才会改变采集指标。

## 六项权重与真实采分点

| 维度 | 上限 | 主要公开信号 |
| --- | ---: | --- |
| 账号成熟度 | 10 | 账号年龄（满 6 年封顶）与有贡献的年份跨度（最多 3 分）。 |
| 原创项目质量 | 18 | 总 stars、单仓最高 stars、最高星项目的社区参与质量，以及最强原创项目的“完整度/实质性”信号。零星但完整、有代码与说明的项目也能获得实质分。 |
| 贡献质量 | 27 | 已合并 PR 数（对数增长，约 200 封顶）、维护者实际拒绝率、创建 issue，以及高影响核心 PR 奖励；大量文档/样式型 PR 可被折扣或封顶。 |
| 生态与维护影响 | 20 | 进入高星仓库的影响力与贡献深度；源码明确把它定位为最难伪造的信号。 |
| 社区影响 | 8 | followers 的对数分及 follower/following 比例；不是单看粉丝数。 |
| 活跃真实性 | 17 | 最近一年贡献数、最近活动时间、活动类型多样性。 |

其中最有杠杆的两项是贡献质量（27）与生态影响（20）。72 个 merged PR 和 165 个 impact PR 已经是强证据；下一步重点应是提升“核心改动的深度和可复核性”，不是机械增加 PR 数。

## 当前红旗的正确处理

`new_account_mass_repos` 的阈值很窄：账号不足一年且公开仓库超过 30，固定 -10。它不会阅读 README，也不判断某个仓库是否“看起来专业”。诚实且低风险的处理顺序是：

1. **等待年龄条件自然解除。** 不为分数删除真实作品；年龄达到一年后重新扫描核验。
2. **以后减少一次性公开占位仓库。** 试验、临时 fork、一次性练习先放本地或私有空间；确需公开时合并为有明确边界的实验仓库，而不是批量新建空壳。
3. **整理已有公开仓库，但不伪造。** 对确实废弃且没有保留价值的占位项目，可在审查后归档或私有化；归档仍属于公开仓库，通常不会改变这条阈值，只有真正减少公开仓库数才可能影响它。不要为了分数隐藏有价值的开源成果。

## 可执行的高分路径（诚实版）

- 选择少量上游项目持续做**可测试的核心修复**：运行时行为、兼容性、数据正确性、并发/可靠性、真实 API 集成。保留 PR、测试与 maintainer review 的公开链路。
- 把已合并贡献沉淀成 1–2 个原创、可运行的项目：清晰 README、可复现安装、测试/CI、版本发布、issue 处理、真实用户反馈。目标不是堆 stars，而是给“原创项目质量”提供可审查的实质信号。
- 继续维持跨月活动，而不是短时间集中投递；真实的代码、issue、review、release 等多种活动会帮助活跃真实性。
- 控制文档/样式类 PR 的比例，不停止做文档，而是让它们与更深的功能、测试、兼容性或故障修复保持平衡。避免把极小改动投向热门仓库来换 contributor 记录。
- 社区关系保持自然：不要用大量 follow 换关注；对 issue、review、维护和用户支持的长期参与，比短期社交数字更稳健。
- 主页继续保留“贡献项目”目录，但每条只写可验证事实和链接。它是人工尽调的证据索引，也是 LLM 报告的背景材料；它不是机器分数的捷径。

## 复核方式

等账号年龄条件改变或产生实质新工作后，调用 ghfind 的公开 `GET /api/score/uuzzrm` 或完整 scan，记录新分数、六项子分、红旗和采集时间；不要将旧快照与新扫描混用。对 merged PR 的真实性，仍以 GitHub PR 的 `mergedAt` 为准。
